The big correction

Earlier I inferred NRVNA was a "privacy-first personal-AI project" with imgsrch as one app. The real (documented) story: NRVNA is a set of local inference primitives, and imgsrch is a composition example built on them.

AGENTS.md states NRVNA provides "durable local inference through three command-line primitives: wrk submits jobs, nrvnad executes them, and flw reads results." It is explicitly "not a chat API or an agent framework" — it's designed to compose with "processes, exit codes, JSON, and files." imgsrch is built with "nrvna, local async inference primitives."

So the "durable background indexing" INSTALL.md mentioned is really the NRVNA daemon draining a job queue.

The seven concepts you asked about (as documented)

Job
- A wrk submission creates "an independent durable task."
- Jobs become immutable once "published under input/ready/" and produce terminal artifacts: result.txt, embedding.json, or error.txt.

Context
- Strict isolation: "Context does not carry between jobs." Evidence must be "put in the next prompt explicitly" — nothing is passed implicitly. (AGENTS.md slogan: "The workspace remembers; the model does not.")

Lineage
- --parent "records lineage only: it does not copy context, wait for the parent, or impose execution order."
- You can retrieve "direct descendants" via flw --children.
- Key distinction: lineage is provenance/bookkeeping, not dataflow or scheduling. A child does not inherit the parent's context and does not wait on it.

Daemon (nrvnad)
- A single nrvnad process "owns a workspace at a time."
- Two modes: run persistently for "repeated low-latency work," or use --drain for "bounded batches, model swapping, and constrained hardware."

Drain (--drain)
- "loads the model, lets up to two workers process the queue, and exits at observed idle" — enabling graceful shutdown and model swapping.
- This is exactly what INSTALL.md's "each model loads, drains its queue, and exits" refers to. Concurrency cap: up to two workers.

Durability
- "Submission is staged and atomically published" (stage → atomic publish, so no half-written jobs become visible).
- After crashes, "the next daemon recovers abandoned processing/ jobs."
- Job state lives in the filesystem under workspaces/ — job queues are "inspectable mid-flight."

Failure semantics
- Execution is at least once.
- "Failures are terminal and preserved under failed/."
- Retry logic "belongs to the calling app or agent, not the primitive."

Confirmed — and importantly, tags are documented (I was right not to assume). AGENTS.md shows the literal pattern: repeated --tag <name> on wrk, then flw <ws> -W --tag <name> as a batch barrier. Here's the design, built only from those verbatim contracts.

Documented contracts I'm relying on

- wrk <ws> <prompt> → stages a job, prints job ID to stdout; - reads the prompt from stdin; --tag <name> labels it; --parent <id> records lineage only.
- nrvnad <model> <ws> [--workers N] [--drain] → one daemon owns the workspace; --drain "loads the model, lets up to two workers process the queue, and exits at observed idle." nrvnad stop <ws> stops a persistent one.
- flw <ws> <job> → exits 0 done, 1 failed, 2 not ready; --json for machine output; -w waits on one job; -W --tag <name> is a barrier for a whole tagged batch.
- Durability: submission is staged and atomically published under input/ready/; a crash leaves jobs in processing/, recovered by the next daemon; failures are terminal, preserved under failed/; execution is at least once; retries belong to the caller; context does not carry between jobs.

The batch workflow (20 text files, one model)

Because context never carries between jobs and there are no dependencies, this is 20 independent, self-contained jobs sharing one tag — no --parent.

BIN=/path/to/bin
WS=/path/to/workspace          # an existing nrvna workspace the daemon will own
MODEL=/path/to/model
TAG=batch-2026-07-22

# 1) Submit all 20 first, so the queue is fully staged before draining.
#    Each file's content becomes one job's prompt (via stdin), self-contained.
: > jobids.txt
for f in /path/to/texts/*.txt; do
  JOB=$("$BIN/wrk" "$WS" - --tag "$TAG" < "$f")
  printf '%s\t%s\n' "$JOB" "$f" >> jobids.txt
done

# 2) Drain the queue with one model load, up to two workers, then exit at idle.
"$BIN/nrvnad" "$MODEL" "$WS" --workers 2 --drain

# 3) Barrier: block until every job carrying this tag is terminal.
"$BIN/flw" "$WS" -W --tag "$TAG"

# 4) Collect results / classify each job by its documented exit code.
while IFS=$'\t' read -r JOB f; do
  if "$BIN/flw" "$WS" "$JOB" --json > "results/$JOB.json"; then
    echo "done: $JOB ($f)"          # exit 0
  else
    code=$?
    if [ "$code" -eq 1 ]; then
      echo "FAILED: $JOB ($f)"      # exit 1 → artifact under failed/, terminal
    else
      echo "NOT READY: $JOB ($f)"   # exit 2 → shouldn't happen post-barrier
    fi
  fi
done < jobids.txt

Why submit-before-drain: --drain "exits at observed idle." If you start the daemon against an empty/slow-filling queue it can hit idle and quit early. Staging all 20 first (submission is independent of the daemon — it publishes to input/ready/) matches the documented cold-run order: wrk … → nrvnad … --drain → flw ….

Tags

- Purpose here: a batch barrier, not routing or context. You put the same --tag "$TAG" on all 20 submissions, then flw "$WS" -W --tag "$TAG" blocks until the whole labeled set is terminal — the documented way to "wait for this batch" without tracking 20 IDs by hand.
- Tags carry no execution semantics beyond grouping. They don't imply ordering, dependency, or shared context.
- (You still keep the per-job IDs from wrk stdout so you can read individual results and tell which file each maps to — the tag groups them but doesn't name them.)

Drain behavior

- One --drain run = one model load, up to two concurrent workers, processes whatever is in the queue, exits at observed idle. Ideal for a bounded 20-file batch on constrained hardware or when you want the model unloaded afterward.
- No ordering guarantee across the 2 workers; the 20 jobs may complete in any order. That's fine because each is independent.

Failure handling

- Execution is at least once — a job could run more than once across a crash/recovery, so treat processing as idempotent (a pure text→text transform is).
- A crashed daemon leaves work in processing/; the next nrvnad recovers it. If your single --drain run dies mid-batch, some jobs stay non-terminal — the barrier in step 3 won't complete. Recovery = run nrvnad … --drain again; it resumes the abandoned jobs.
- Failures are terminal and preserved under failed/; flw returns exit 1 for those. There are no automatic retries. If you want to retry a failed file, that's a brand-new wrk submission (new job ID) — the primitive won't do it for you.

What remains the caller's responsibility (i.e., yours)

- Workspace lifecycle — ensuring a single daemon owns $WS at a time, and that the workspace exists. (Gap: the docs I've read show wrk/nrvnad operating on an existing $WS but don't show a bare-nrvna "create workspace" command — imgsrch has its own init, but I won't assume that maps to the primitive. Flagging this as the one unresolved detail.)
- Job-ID tracking and the ID→file mapping (capturing wrk stdout).
- Prompt construction — every job must be fully self-contained; nothing is inherited, so any instructions/context must be inlined into each file's prompt.
- Barrier + polling policy — choosing -W --tag vs. per-job -w/exit-code checks.
- Failure classification and retry policy — scanning failed/ / exit codes and deciding whether/how to resubmit.
- Output validation and aggregation — combining the 20 result artifacts into whatever you actually need.
- Model selection and the drain-vs-persistent decision.

Explicitly not assumed (per your constraint)

- No --parent / no lineage — the 20 files are independent; I introduced no parent-child edges.
- No inherited context — each prompt stands alone.
- No automatic retries — failures stay in failed/; any retry is a new job.
- No undocumented features — everything above maps to a quoted contract, and I called out the single spot (workspace creation for the bare primitive) where the docs I read don't specify the command.

What NRVNA actually is

NRVNA is a durable, local, filesystem-based job queue for model inference — a "batch scheduler for one machine." Strip away the framing and that's the mechanism I just watched work:

- You drop a job on disk (wrk → input/writing/ → atomically → input/ready/).
- A daemon (nrvnad) loads a model, claims jobs, writes results to output/<job>/, and exits when idle.
- You read results back by file + exit code (flw).

The filesystem is the database. There's no server, no socket, no session — state is directories (writing → ready → processing → output/failed). That's why it's durable and crash-recoverable: a job is just files, and "recovery" is re-scanning directories. I confirmed the decoupling directly — I submitted, waited 22 seconds with no daemon alive, then started one and it picked the job up. Submission and execution are genuinely independent.

What kind of thing it is (and isn't)

It's a primitive, deliberately dumb in the right ways:
- The model is stateless; the workspace is stateful. Load model → drain queue → unload. That "drain" mode (verified: 2 workers, load-once, exit-at-idle) is the whole trick for running real models on a laptop without a resident GPU service.
- No orchestration. No retries, no context passing, no dependency execution — lineage (--parent) is provenance only. All the "smarts" live in the caller. It's Unix pipes for inference: small tool, composes via files and exit codes.
- It is explicitly not a chat API or agent framework, and after running it, that's obviously true — there's nothing conversational about it. It's make / xargs for model calls.

Where imgsrch fits (now clearer)

imgsrch is a caller built on this. Its "durable background indexing" that INSTALL.md bragged about is literally this: imgsrch index submits N embed/caption/OCR jobs to a NRVNA workspace, and nrvnad drains them. I just ran, by hand, the exact primitive imgsrch drives underneath. The embedding job I executed (nomic-embed-text, 768-dim, L2-normalized) is one leg of imgsrch's combined.md → embedding.json pipeline — same model, same artifact name.

The honest one-liner

NRVNA is local inference reimagined as durable Unix jobs: submit a prompt as a file, a drain-and-exit daemon runs it against a GGUF model, results are files you read by exit code — and everything above that (retries, context, search, agents) is your problem, by design.

What I now know (ran it): the queue/daemon/drain/durability/exit-code contract is real and behaves as documented. What's still inference: the broader intent — I strongly suspect NRVNA is meant as the substrate for a family of local, agent-callable apps (imgsrch being the first), because the whole design screams "built to be composed by higher-level callers." But no doc I've read states a roadmap, so I'm holding that as a well-supported guess, not a fact.

  ## imgsrch

  I like imgsrch a lot. It solves a mundane, widespread problem in a way
  that demonstrates local AI without requiring users to care about local
  AI.

  Its strongest quality is that the architecture matches the problem:

  - OCR finds exact visible language.
  - Captions describe meaning and visual context.
  - BM25 preserves lexical precision.
  - Embeddings handle semantic intent.
  - RRF combines independent retrieval signals without pretending one
    score is universally correct.

  - Original files remain the source of truth.
  - Agents receive a small candidate set instead of hundreds of
    screenshots.

  That is not decorative model composition. Each component compensates
  for another component’s weakness.

  The product sentence is excellent:

  > Search local screenshots and images by what they say and what they
  > mean.

  It works for both humans and agents, but I would market it human-first:

  > Local semantic search for screenshots—use it directly, or let an
  > agent retrieve only the images relevant to its task.

  My remaining uncertainty is retrieval quality at realistic scale. Three
  indexed images proved installation and mechanics, not search quality.
  Before claiming “powerful” or “high-quality,” I would test:

  - several hundred real screenshots;
  - exact text queries;
  - vague semantic queries;
  - visually similar screenshots;
  - screenshots with tiny OCR text;
  - queries where captioning and OCR disagree;
  - recall@1, recall@3, and recall@5;
  - a handful of honest failure cases.

  I nevertheless think imgsrch is ready for an early technical release
  once the installation/package mismatch and platform smoke tests are
  resolved.

  ## NRVNA

  NRVNA is more interesting than I initially understood.

  At first glance, nrvnad, wrk, and flw can look like a thin local
  inference wrapper. After using them, the real idea became clearer:

  > Inference is submitted work, not necessarily a live request.

  That is a meaningful distinction.

  Ollama, LM Studio, and llama-server primarily make a model available as
  a service. An async SDK prevents an application thread from blocking,
  but the work usually remains attached to an active run or request.

  NRVNA changes the lifecycle:

  submit work → leave → compute becomes available → retrieve artifacts

  Its most compelling qualities are:

  - submission does not require a currently running model;
  - submitter and executor have independent lifetimes;
  - constrained hardware can load a model, drain work, and release
    memory;

  - powerful hardware can keep several model workers resident;
  - fresh context is the default;
  - files preserve inputs, results, and lineage;
  - models can be composed without sharing context;
  - artifacts can be inspected and indexed by ordinary tools;
  - a larger agent can initiate local work and conclude it later.

  The best conceptual line remains:

  > An async SDK makes waiting non-blocking. NRVNA makes the work
  > independent of the waiter.

  And the deepest architectural line may be:

  > The model forgets; the workspace remembers.

  That feels particularly appropriate for local AI. It does not try to
  make a small local model imitate an infinitely stateful cloud chatbot.
  It lets small models perform bounded, repeatable transformations while
  the surrounding system supplies persistence and composition.

  ## Where NRVNA is genuinely distinctive

  None of the individual ingredients is unprecedented:

  - filesystem spools exist;
  - worker queues exist;
  - batch inference exists;
  - local model servers exist;
  - shell pipelines exist;
  - workflow engines exist.

  The distinctive part is their combination at this scale:

  > Local inference, submitted without a live server, persisted as open
  > filesystem artifacts, processed when compute is available, and
  > composable with Unix-like tools.

  That occupies a useful space between:

  direct model CLI
          ↓
        NRVNA
          ↓
  application workflow
          ↓
  large agent framework / distributed workflow engine

  It is lightweight enough for Bash and powerful enough to underpin
  imgsrch. That is a good sign: the abstraction has already produced a
  real application rather than only a framework demo.

  ## What concerns me

  The main risk is not overengineering. It is semantic ambiguity.

  Several names and behaviors invite stronger assumptions than the
  implementation currently supports:

  - flw sounds like a workflow engine, but it retrieves and observes
    work.

  - --parent sounds like context or dependency, but currently means
    lineage.

  - “queue” may imply retries, atomic claims, delivery guarantees, and
    crash recovery.

  - A workspace may appear permanently model-bound, but the daemon
    selects the model at runtime.

  - Swapping a daemon’s model could process previously queued work with
    an unexpected model.

  - “Durable” needs a stated failure boundary.
  - Exact model, prompt, configuration, and output-schema provenance need
    to accompany artifacts.

  - wrk collides with the widely known HTTP benchmark.
  - The failed nrvnad stop behavior needs resolution.
  - The missing ADVANCED.md reference weakens the self-contained release.

  None of these invalidates the architecture. They are signs that the
  implementation has reached the point where its contract matters.

  My highest-priority NRVNA improvements would be:

  1. Record the exact model, revision, prompt version, runtime
     configuration, and NRVNA version for every result.

  2. Document fresh-context, parent, workspace, and daemon semantics
     explicitly.

  3. Define crash, retry, duplicate, and concurrent-worker guarantees.
  4. Provide one supported two-model composition recipe.
  5. Add minimal dependency semantics only after real applications demand
     them.

  6. Stabilize compact machine-readable output so agents do not ingest
     enormous embeddings accidentally.

  I would not rush to add chat memory, MCP, distributed brokers, or a
  large workflow language.

  ## How the two products should relate

  imgsrch should lead publicly because it supplies the immediate “why.”

  Problem: I cannot find my screenshots.
  Product: imgsrch.
  Question: How can three local models do this asynchronously?
  Answer: NRVNA.

  That story is stronger than launching NRVNA as an abstract framework
  and asking developers to imagine applications.

  imgsrch is the evidence that NRVNA’s primitives are useful:

  - caption and OCR can run independently;
  - their artifacts can be joined;
  - embeddings can be regenerated separately;
  - indexing can outlive the initiating agent;
  - search can happen in a later session;
  - no chat thread has to carry the state.
