What is your company going to make? Please describe your product and what it does or will do.
nrvna ai is building the inference primitive for AI - a missing layer between chats and agents.

Once your prompt, model, and task are dialed in, you can graduate out of the chat window. There's no need for more experimentation and you just need a clean, reliable way to submit, repeat, and scale inference without orchestration complexity or framework bloat. Most tasks are one-shot inferences, not agents.

nrvna is a Unix-style, asynchronous runtime powered by llama.cpp. You start a daemon with ./nrvna <workspace> <model>, submit jobs using ./wrk <workspace> <input + prompt>, and retrieve results with ./flw <workspace>. Everything is a file the input, output, metadata. It’s stateless, composable, and local-first by design.

* Want multiple models? Start another daemon.
* Want to push jobs from another device? Use a simple HTTP `POST`.
* Want to run 100 prompts as part of eval? Just write a shell script.

It runs anywhere from your laptop, the cloud, an embedded device, or on a rack of Raspberry Pis. Use it standalone to build CLI-first LLM apps, or as backend infra for agents, pipelines, or enterprise tools.

Late interaction is relevant, but the post is discussing a
  broader layer.

  Query understanding
          ↓
  Metadata filtering
          ↓
  Candidate retrieval (L0)
    ├─ BM25
    ├─ single-vector dense      ← imgsrch today
    └─ late interaction        ← ColBERT/ColPali option
          ↓
  Fusion
          ↓
  Reranking

  Late interaction improves candidate retrieval. Instead of
  compressing the entire caption into one vector, it retains
  vectors for individual tokens or image patches and uses
  MaxSim matching.

  That could help imgsrch retrieve:

  - A rare technical detail buried in a long caption
  - A small relevant region of a screenshot
  - Concepts where most screenshot content is unrelated
    noise

  - Visually grounded evidence that captions or OCR missed

  It could therefore produce a much better L0 candidate set
  than the current single 768-dimensional vector.

  But it does not solve the whole problem in the screenshot:

  - It does not enforce “from LinkedIn.”
  - It does not enforce “saved this week.”
  - It does not inherently distinguish “material for my
    interview” from “a post discussing ML interviews.”

  - It cannot recover metadata that was never indexed.

  So the complete future design could be:

  query understanding + metadata filters
                     ↓
  ColPali/ColBERT late-interaction retrieval
                     +
                   BM25
                     ↓
  optional fusion or reranking

  Late interaction may reduce dependence on RRF because one
  retrieval channel captures both semantic meaning and
  localized high-signal details better. It probably would
  not eliminate BM25 for exact identifiers such as
  llama.cpp, names, URLs, or error messages.

  So: yes, late interaction is one strong answer to the
  post’s “better L0 candidates” argument. It is not an
  answer to missing metadata or query understanding.
